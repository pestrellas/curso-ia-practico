Técnica 01 — Zero-Shot Prompting

Sin ejemplos: aprovecha el preentrenamiento

Se pide al modelo ejecutar una tarea sin demostración previa. La instrucción por sí sola —con rol, tarea y formato bien definidos— debe ser suficiente para que infiera la respuesta correcta.

ANATOMÍA DE UN PROMPT ZERO-SHOT ROBUSTO
ROL Eres un sistema de triaje de soporte técnico.
TAREA Asigna una PRIORIDAD (Alta / Media / Baja) y una CATEGORÍA (Acceso / Red / Software / Otro) al siguiente ticket.
REGLAS Alta = impacto en producción o pérdida de datos. Media = afecta a un departamento. Baja = consultas o mejoras.
FORMATO Responde SOLO en JSON: {"ticket_id": "...", "prioridad": "...", "categoria": "...", "razonamiento": "..."}
INPUT Ticket #2047: "El equipo de contabilidad en Guayaquil no puede acceder al ERP desde esta mañana."

🏢 Recursos Humanos 
Eres un asistente de RRHH.
Clasifica la siguiente queja laboral
en una de estas categorías:
[Ambiente / Salario / Discriminación / 
Carga de Trabajo / Otro].
Devuelve: { "categoria": "...",
"urgencia": "alta|media|baja" }

Mensaje: "Trabajo más horas que mis
colegas pero recibo el mismo sueldo."
⚖️ Legal / Documental 
Eres un asistente legal liviano.
Extrae del contrato entre triples
comillas los campos: partes, vigencia,
objeto y cláusulas de penalización.
Si un campo no existe, escribe
"no_disponible". Formato: JSON.

"""El presente acuerdo entre
Alpha Corp. y Beta S.A., vigente
del 1/01/2025 al 31/12/2025...
"""

✅ Mejores casos de uso

  • Clasificación de texto con categorías estándar
  • Resumen y extracción estructurada
  • Reformulación y traducción
  • Moderación de contenido
  • Prototipado y borradores iniciales
  • Generación de código genérico

🚫 Cuándo evitarlo

  • Tareas con formato de salida muy específico o propietario
  • Dominio especializado o jerga interna
  • Cuando la salida es inconsistente entre llamadas
  • Razonamiento multi-paso no trivial
  • Categorías de clasificación no estándar

🔧 Mejores prácticas

  • Define el rol del modelo antes de la tarea
  • Usa verbos de acción precisos: clasifica, extrae, resume
  • Especifica el formato exacto de salida (JSON, tabla, lista)
  • Incluye restricciones observables (longitud, tono, idioma)
  • Añade una respuesta de escape: dato_no_disponible
  • Evalúa primero zero-shot antes de agregar complejidad

📏 Señales para escalar a Few-Shot

  • El formato de salida es inconsistente entre ejecuciones
  • El modelo acierta el fondo pero falla en el estilo o tono
  • Hay categorías propietarias difíciles de describir
  • 3–5 ejemplos bien elegidos corregirían el problema
  • La tarea tiene reglas tácitas que no se verbalizan bien
ℹ️

Plantilla robusta Zero-Shot: "Eres [rol]. Tu tarea es [descripción]. Usa solo el contexto entre triple comilla. Si falta evidencia, responde dato_no_disponible. Devuelve JSON con este esquema: [esquema]."

Técnica 02 — Few-Shot Prompting

Con ejemplos: in-context learning sin fine-tuning

Se incluyen 2–5 pares de entrada-salida en el prompt. El modelo aprende el patrón, el formato y los criterios de decisión desde el contexto, sin actualizar sus pesos ni requerir re-entrenamiento.

ANATOMÍA DE UN PROMPT FEW-SHOT BIEN CURADO
ROL Eres un sistema de análisis de sentimiento para reseñas de clientes.
TAREA Clasifica el sentimiento de la reseña como: positivo | neutro | negativo. Responde SOLO la etiqueta.
EJEMPLO 1 Reseña: "El servicio fue excelente, muy recomendado." → positivo
EJEMPLO 2 Reseña: "El producto llegó tarde y dañado." → negativo
EJEMPLO 3 Reseña: "El artículo es como se describe, ni más ni menos." → neutro
CONSULTA Reseña: "Me esperaba más del producto por el precio que tiene." → ?

✅ Mejores casos de uso

  • Clasificación con categorías propietarias
  • Extracción de entidades en formato estándar
  • Generación de salidas JSON / YAML consistentes
  • Traducción de jerga especializada
  • Análisis de sentimiento con etiquetas propias
  • Transcripción médica o legal con estilo uniforme

⚠️ Riesgos documentados

  • Sesgo de recencia: tiende a repetir la última etiqueta del prompt (Zhao et al., 2021)
  • Sesgo de etiqueta mayoritaria: sesga hacia la clase más frecuente entre los ejemplos
  • Sesgo de token común: prefiere respuestas frecuentes en preentrenamiento
  • Orden importa: permutaciones pueden llevar de 90% a rendimiento aleatorio
  • Modelos de razonamiento: few-shot puede degradar (o1, DeepSeek-R1)

🔧 Mejores prácticas

  • Selecciona ejemplos diversos y representativos del dominio
  • Mantén formato idéntico entre todos los ejemplos y la consulta
  • Incluye casos límite o errores corregidos para mayor robustez
  • Ordena los ejemplos de forma aleatoria o por similitud con el input
  • Empieza con zero-shot; añade ejemplos solo si hay inconsistencia
  • Prioriza calidad sobre cantidad; nunca excedas la ventana de contexto

📐 Cuántos ejemplos usar

  • 1 ejemplo (One-Shot): cuando el patrón es muy simple y uniforme
  • 2–3 ejemplos: balance óptimo costo/beneficio en la mayoría de casos
  • 3–5 ejemplos: recomendación explícita de Anthropic para mayor consistencia
  • 5–9 ejemplos: tareas complejas; vigilar sesgos y costo de tokens
  • +10 ejemplos: rendimientos marginales decrecientes; considerar fine-tuning
⚠️

Few-shot mal curado es una ruleta elegante. La literatura muestra que ejemplos semánticamente cercanos al input objetivo superan a la selección aleatoria, y que algunas permutaciones del prompt pueden marcar la diferencia entre el estado del arte y un rendimiento casi aleatorio. Curar ejemplos requiere la misma disciplina que diseñar los prompts.

Análisis Comparativo

Zero-Shot vs. Few-Shot: matriz de decisión

No existe una técnica superior en términos absolutos. La elección depende del tipo de tarea, el modelo, el costo de tokens y la consistencia requerida.

Dimensión Zero-Shot Few-Shot
Complejidad del prompt Muy baja — solo instrucción Baja-Media — crece con ejemplos
Costo en tokens Muy bajo — mínimo necesario Medio — aumenta por cada ejemplo
Tiempo de preparación Mínimo — redactar instrucción Mayor — curar y validar ejemplos
Consistencia de formato Variable — puede desviarse Alta — los ejemplos anclan el formato
Transferencia de estilo Limitada — depende del entrenamiento Alta — los ejemplos transmiten el tono
Categorías propietarias Difícil — difícil describir sin ejemplos Natural — los ejemplos ilustran la categoría
Riesgo de sesgo Bajo — no hay ejemplos que sesgar Medio-Alto — recencia, mayoría, orden
Modelos de razonamiento (o1, R1) Recomendado — empezar siempre aquí Cuidado — puede degradar el rendimiento
Tarea de clasificación simple Ideal Válido si falla zero-shot
Generación de salidas JSON Posible con instrucción detallada Superior — ejemplos anclan el esquema
Velocidad de prototipado Alta Moderada
Escalabilidad en producción Excelente — bajo costo por llamada Buena — vigilar ventana de contexto
📌

Regla operativa: Si la tarea es sencilla y el formato está claro, empieza con zero-shot. Si el modelo entiende la tarea pero "contesta bien la forma y mal el fondo", o produce salidas inconsistentes, agrega few-shot. Zero-shot es la línea base obligatoria antes de agregar cualquier complejidad.

Herramienta Interactiva

Simulador: la misma tarea, dos enfoques

Observa cómo se estructura el mismo problema como Zero-Shot vs. Few-Shot. El simulador muestra la diferencia arquitectónica y el razonamiento detrás de cada elección.

⚙️ TAREA: Clasificación de emails de soporte
📧 CONTEXTO: Necesitas clasificar emails entrantes en categorías de prioridad para un equipo de soporte.
Eres un clasificador de soporte al cliente. Clasifica el siguiente email según su PRIORIDAD y TIPO: - PRIORIDAD: Crítica | Alta | Media | Baja - TIPO: Fallo técnico | Consulta | Facturación | Reclamo | Otro Criterios: Crítica = servicio caído, pérdida de datos, bloqueo total Alta = degradación de servicio, múltiples usuarios afectados Media = usuario individual afectado, solución disponible Baja = pregunta informativa, sugerencia Responde en JSON: {"prioridad": "...", "tipo": "...", "accion": "..."} Email: "Buenos días, llevo 3 horas sin poder iniciar sesión en la plataforma. Mi equipo de 15 personas está parado." // Sin ejemplos — el modelo infiere desde la instrucción y su preentrenamiento
¿Por qué funciona aquí? La tarea es clasificación estándar con criterios explicitables en texto. Los conceptos "Crítica", "Alta", etc., están bien definidos en la instrucción. No hay jerga propietaria que requiera demostración. El formato JSON ancla la salida. Zero-shot es suficiente y más eficiente.
📧 CONTEXTO: Ahora las categorías son internas y el tono de respuesta debe ser muy específico (estilo de marca).
Eres un clasificador de soporte con estilo de marca ACME. Clasifica emails y genera un primer párrafo de respuesta con el tono cálido y profesional de ACME. --- EJEMPLO 1 --- Email: "El módulo de pagos no carga desde ayer." {"nivel": "P1", "tipo": "Técnico-Crítico", "respuesta_inicio": "Hola, lamentamos los inconvenientes. Nuestro equipo técnico ya fue notificado y está trabajando en este momento para resolver tu caso con máxima prioridad."} --- EJEMPLO 2 --- Email: "¿Cuánto cuesta actualizar a Enterprise?" {"nivel": "P3", "tipo": "Comercial-Consulta", "respuesta_inicio": "¡Hola! Gracias por tu interés en crecer con ACME. Me complace compartirte nuestras opciones de Enterprise, diseñadas para equipos como el tuyo."} --- EJEMPLO 3 --- Email: "Me cobraron dos veces el mismo mes." {"nivel": "P2", "tipo": "Facturación-Reclamo", "respuesta_inicio": "Hola, entendemos la preocupación y pedimos disculpas por el inconveniente. Revisamos tu cuenta de inmediato y te confirmamos el proceso de reembolso."} --- CONSULTA --- Email: "Llevo 3 horas sin poder iniciar sesión. Mi equipo de 15 personas está parado." // Los ejemplos transmiten: categorías internas (P1/P2/P3), tono de marca ACME, formato exacto
¿Por qué few-shot aquí? Las categorías son propietarias (P1/P2/P3 no son estándares universales). El tono "cálido y profesional de ACME" es imposible de describir solo con palabras — los ejemplos lo demuestran. El formato del campo respuesta_inicio también requiere mostrar el estilo. Zero-shot aquí sería inconsistente.
Uso en Conjunto

Zero-Shot + Few-Shot: el flujo iterativo

En la práctica, los equipos no eligen una técnica y la mantienen para siempre. Usan zero-shot como punto de partida y añaden ejemplos solo cuando la evidencia los justifica. Este flujo iterativo optimiza calidad y costo simultáneamente.

Paso 01
Zero-Shot base
Escribe la instrucción con rol, tarea, formato y restricciones. Sin ejemplos.
→
Paso 02
Evaluar salida
¿Es consistente el formato? ¿El tono es correcto? ¿Falla en casos límite?
→
Paso 03
Añadir Few-Shot
Solo si zero-shot falla: agrega 2–3 ejemplos que corrijan el error observado.
🔀 Árbol de Decisión: ¿Qué técnica usar?
Q1
¿Es un modelo de razonamiento? (o1, DeepSeek-R1, Gemini Thinking)

Los modelos de razonamiento ya incorporan CoT interno. Few-shot puede degradar su rendimiento al interferir con su proceso de "pensar".

SÍ → Zero-Shot siempre primero NO → Continúa al Q2
Q2
¿Puedes describir la tarea completa en instrucciones de texto?

Criterios, categorías, restricciones y formato pueden verbalizarse sin ambigüedad. El modelo generaliza desde preentrenamiento.

SÍ → Usa Zero-Shot NO → Continúa al Q3
Q3
¿Ya probaste Zero-Shot y la salida es inconsistente o con formato incorrecto?

La regla es: medir primero, luego complejizar. Si zero-shot ya funciona, no agregues complejidad innecesaria.

SÍ → Añade Few-Shot (2–5 ejemplos) NO → Ajusta la instrucción zero-shot
Q4
¿Las categorías son propietarias o el estilo es muy específico?

Categorías internas, tono de marca, terminología especializada: situaciones donde los ejemplos transmiten lo que las palabras no pueden.

SÍ → Few-Shot directo (sin pasar por zero-shot) NO → Zero-Shot con instrucción refinada
Q5
¿3–5 ejemplos no mejoran la precisión o introducen sesgo de recencia?

Si few-shot no resuelve el problema, el camino se bifurca hacia Chain-of-Thought (para razonamiento) o hacia fine-tuning (para dominio muy especializado).

SÍ → Evalúa Chain-of-Thought o fine-tuning NO → Few-Shot resuelto ✓

💡

Patrón de producción más frecuente: En entornos reales, los equipos combinan Zero-Shot y Few-Shot más que otras técnicas. Zero-shot para el primer paso (detección, clasificación rápida, extracción) y few-shot para pasos que requieren estilo o formato propietario (generación de respuestas, transformaciones con esquema fijo). La evidencia muestra que la mayoría de equipos usan combinaciones (Zero/Few-Shot + Chaining) más que técnicas aisladas en producción.

Referencia Rápida

Cheat sheet para instructores y profesionales

Síntesis accionable de ambas técnicas y su uso combinado.

Zero-Shot

Línea base obligatoria — evalúa siempre aquí primero
Verbos precisos: clasifica, extrae, resume, traduce
Especifica formato (JSON, lista, tabla) explícitamente
Define un rol claro antes de la tarea
Incluye escape: si falta evidencia → dato_no_disponible
Ideal para modelos de razonamiento (o1, R1)
Métricas: exact match, schema-valid rate, ROUGE/BLEU

Few-Shot

Agrega solo si zero-shot falla en formato o consistencia
3–5 ejemplos es el rango óptimo (Anthropic)
Diversidad > cantidad: cubre casos límite
Formato idéntico entre todos los ejemplos y la consulta
Vigila sesgo de recencia (último ejemplo → sesgo de salida)
Ejemplos cercanos al input superan a los aleatorios
No usar con o1/R1 sin probar zero-shot primero

Uso Conjunto

Zero-shot primero, few-shot solo si falla: no al revés
Zero para detección rápida; few para estilo y formato propietario
Combínalos en pipelines: etapa 1 ZS → etapa 2 FS
Mide cada técnica por separado antes de combinar
Si few-shot no mejora: replantea orden de ejemplos
Si aún falla: considera Chain-of-Thought o fine-tuning
En producción: monitorea costo por token vs ganancia de precisión
