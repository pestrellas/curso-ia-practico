Chain of Thought Prompting: razonamiento estructurado para tareas complejas

Chain of Thought —CoT— consiste en pedir al modelo que descomponga una tarea antes de responder. Su valor aparece cuando hay múltiples pasos de inferencia, cálculos, restricciones o decisiones que conviene revisar.

Qué cambia
Pregunta → análisis estructurado → respuesta final.
Variantes
Zero-Shot CoT, Few-Shot CoT y Self-Consistency.
Útil para
Matemáticas, lógica, diagnóstico, código y decisiones.
Cuidado con
Más latencia, más tokens y falsa sensación de explicabilidad.
🧠
Punto fino: CoT no debe entenderse como acceso garantizado al “pensamiento interno” del modelo. Es una técnica para obtener razonamiento estructurado, revisar pasos y mejorar consistencia en tareas donde la respuesta directa puede ser frágil.

Resumen claro

Qué es CoT y por qué importa

El prompting estándar pide una respuesta. CoT pide que el modelo organice la ruta hacia esa respuesta. Eso ayuda cuando el problema exige varios pasos verificables.

Idea base

Razonar antes de cerrar

El modelo separa datos, reglas, pasos intermedios y conclusión. La salida deja de ser una caja negra de una sola línea.

Aplicación

Descomponer problemas

Sirve para cálculos encadenados, lógica, planificación, diagnóstico, análisis legal o depuración de código.

Advertencia

No todo lo necesita

En tareas simples, CoT puede agregar costo, ruido y errores. La técnica tiene sentido cuando los pasos importan.

01

Entrada

El usuario entrega la pregunta, datos o caso a resolver.

02

Descomposición

El modelo identifica variables, condiciones y restricciones relevantes.

03

Proceso

Se aplican reglas, cálculos, comparaciones o inferencias.

04

Verificación

Se revisa coherencia antes de emitir la conclusión.

05

Respuesta

La salida final queda fundamentada y más fácil de auditar.

Dos variantes principales

Zero-Shot CoT vs Few-Shot CoT

La diferencia está en cómo activas el razonamiento: con una frase simple o con ejemplos completos de cómo debe resolverse el problema.

Zero-Shot CoT

Un trigger activa el razonamiento

Rol: Eres un analista de proyectos.

Tarea: Evalúa si el proyecto es viable considerando mercado, competencia, margen y retorno.

Caso: App de delivery en ciudad de 80.000 habitantes.
Inversión inicial: 50.000 USD.
Competidores: 3 apps activas.
Margen estimado por pedido: 1,20 USD.

Trigger: Analiza paso a paso antes de emitir el veredicto final.
Más rápido de implementar.
Útil cuando el modelo ya conoce bien la tarea.
Agrega pocos tokens respecto a un prompt estándar.
Few-Shot CoT

Ejemplos enseñan el patrón

// Ejemplo con razonamiento
Problema: María tiene 3 cajas. Cada caja tiene 4 pelotas.
Paso 1: número de cajas = 3
Paso 2: pelotas por caja = 4
Paso 3: total = 3 × 4 = 12
Respuesta: 12 pelotas.

// Ahora resuelve
Problema: Juan tiene 5 estantes. Cada estante tiene 7 libros.
Más consistente en formato.
Útil si necesitas enseñar una estructura exacta.
Consume más tokens y puede aumentar latencia.
Regla práctica: empieza con Zero-Shot CoT. Usa Few-Shot CoT solo si necesitas controlar formato, criterios o estilo de razonamiento con ejemplos.
Activación Zero-Shot

Triggers que orientan el razonamiento

Un trigger es una frase breve que le dice al modelo cómo ejecutar la tarea. No todos funcionan igual: conviene alinearlo con el dominio.

Trigger Dominio recomendado Uso práctico
“Piensa paso a paso” Matemáticas y lógica Útil cuando la respuesta depende de cálculos o inferencias encadenadas.
“Analicemos sistemáticamente” Negocios y estrategia Ayuda a revisar factores antes de concluir.
“Desglosemos el problema” Código y debugging Orienta a identificar causa raíz, mecanismo y solución.
“Examinemos los datos metódicamente” Análisis de datos Favorece revisión de variables, supuestos y patrones.
“Primero analiza; luego revisa” Diagnóstico y revisión Introduce una segunda mirada antes de cerrar la respuesta.
Tip operativo: coloca el trigger al final del prompt, justo antes de la respuesta esperada. Así funciona como instrucción de ejecución, no como contexto decorativo.
Aplicación práctica

Dónde CoT sí da valor y dónde sobra

CoT es especialmente útil cuando el error puede esconderse en un paso intermedio. Si no hay pasos, probablemente no necesitas CoT.

Úsalo cuando

La tarea tiene razonamiento encadenado

Problemas matemáticos o aritméticos multi-paso.
Razonamiento lógico, deducciones o silogismos.
Planificación con dependencias secuenciales.
Diagnóstico médico, técnico o legal.
Depuración de código con causa raíz trazable.
Decisiones financieras con cálculos encadenados.
Evítalo cuando

La tarea es directa

Clasificación simple de texto.
Resumen o reformulación sin lógica intermedia.
Extracción de entidades con formato estándar.
Traducción directa sin ambigüedad técnica.
Tiempo de respuesta crítico.
Modelos con razonamiento nativo donde CoT manual puede ser redundante.
Finanzas

Cambio regulatorio

Útil cuando hay que calcular impacto y justificarlo.

Prompt: Eres analista de riesgo financiero. Evalúa el capital adicional necesario. Requerimiento sube de 8% a 11%. APR = 2500M USD. Devuelve: 1. capital previo 2. capital nuevo 3. diferencia 4. impacto final
Código

Depuración estructurada

Útil para separar síntoma, causa raíz y solución.

Prompt: Eres senior developer. Diagnostica este error: def calcular_promedio(nums): return sum(nums) / len(nums) result = calcular_promedio([]) Devuelve: 1. causa raíz 2. por qué ocurre 3. corrección mínima 4. corrección robusta
Extensión avanzada

Self-Consistency: varias rutas, una respuesta más confiable

Self-Consistency combina CoT con múltiples cadenas de razonamiento independientes y selecciona la respuesta más frecuente. Es útil cuando un error cuesta caro.

01

Prompt CoT

Se define una tarea que requiere razonamiento estructurado.

02

N intentos

El modelo genera varias cadenas independientes.

03

Diversidad

Las rutas pueden diferir, pero algunas llegan a la misma conclusión.

04

Votación

Se selecciona la respuesta más frecuente.

05

Uso

Reservado para decisiones de alto valor o alta incertidumbre.

Limitaciones críticas

Lo que debes controlar antes de usar CoT

CoT es una herramienta potente, pero no es una capa mágica de verdad. Su uso debe depender del modelo, la tarea y el costo aceptable.

Riesgo 01

No equivale a explicabilidad real

La cadena visible puede ser una reconstrucción plausible, no necesariamente el proceso interno real del modelo.

Riesgo 02

Puede introducir sobre-razonamiento

En tareas simples, pedir pasos puede sumar ruido, tokens y errores que una respuesta directa no tendría.

Riesgo 03

Modelos pequeños pueden fallar

El material original advierte que modelos pequeños pueden producir cadenas fluidas pero ilógicas.

Riesgo 04

Más latencia y más costo

CoT aumenta la longitud de salida. Few-Shot CoT y Self-Consistency multiplican el costo operativo.

Tipo de modelo ¿Usar CoT? Recomendación
LLMs grandes estándar Sí, con criterio Úsalo cuando la tarea tenga múltiples pasos verificables.
Modelos de razonamiento nativo No por defecto Probar primero sin CoT manual; puede ser redundante o interferir.
LLMs medianos Depende Comparar con y sin CoT antes de adoptarlo.
LLMs pequeños Evitar Puede generar pasos convincentes pero incorrectos.
Comparación aplicada

La misma tarea en tres niveles

Así cambia el prompt cuando pasas de una solicitud estándar a CoT y luego a Few-Shot CoT.

Estándar

Respuesta directa

Evalúa si este proyecto es viable. Responde “Viable” o “No viable” y agrega una frase de justificación.

Rápido, pero con poca visibilidad del criterio usado.

Zero-Shot CoT

Análisis estructurado

Evalúa si este proyecto es viable. Considera mercado, competencia, economía unitaria y retorno. Analiza cada factor antes de emitir el veredicto final.

Mejor cuando quieres revisar la ruta de decisión.

Few-Shot CoT

Patrón enseñado

Ejemplo: Proyecto A → mercado limitado, competencia alta, margen bajo. Veredicto: No viable. Ahora evalúa el nuevo proyecto siguiendo el mismo patrón.

Útil si necesitas formato o criterio repetible.

Conclusión

Chain of Thought es útil cuando el razonamiento importa más que la velocidad. No lo uses por reflejo: úsalo cuando necesites descomponer, revisar y justificar. Para tareas simples, una instrucción directa suele ganar. Para decisiones complejas, CoT puede convertir una respuesta opaca en un proceso revisable.

Zero-Shot CoT: rápido, simple y suficiente para muchos casos.
Few-Shot CoT: mejor cuando necesitas enseñar un patrón específico.
Self-Consistency: útil para decisiones de alto valor, pero costosa.
